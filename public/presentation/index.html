The application uses gpt-oss-120b for both chat and memory extraction through DigitalOcean Serverless Inference. CHAT_MODEL and EXTRACTION_MODEL select the same model; their separate names describe responsibilities. Open weights means model weights are available, not that inference is free or that all training data is public. Next.js, React, and TypeScript provide the application; LangGraph coordinates the agent; Tavily provides web search. MongoDB Atlas stores application data and checkpoints. Atlas Automated Embedding uses Voyage voyage-4 for semantic retrieval, separately from the generative model.

THREE PARTS OF AN AI AGENT

01

Reasoning

The LLM interprets a goal,
plans the next step, and
chooses a tool when needed.

02

Tools

Callable functions let the
agent retrieve data and
act on external systems.

03

Memory

Conversation context and

An agent combines reasoning, tools, and memory. A large language model (LLM) interprets the goal and proposes the next action. Application code executes tool functions and handles database access. Memory supplies relevant context to the model; storing a fact does not retrain the model or change its weights.

Fixed workflows suit predictable operations such as required-field validation and fixed-category routing. An agent can help when the next action depends on intermediate results, such as coordinating account lookup and refund-policy evaluation. Consequential actions still need permissions, trusted validation, and appropriate approvals. Claudius Minor exposes web search, not financial actions.

Plan an agent by identifying its tasks, required data, and tools. A tool is a callable function for interacting with external systems. Examples include an API for movie information, a database query for profile settings, or vector retrieval for recommendations. In Claudius Minor, only web_search is model-callable. Memory retrieval runs automatically in the load_context graph node.

Read: No messages table · DEV ↗
Access patterns shape the data model. The thread list reads lightweight records from conversations: owner, title, timestamps, and extraction watermark. The current thread reads messages from LangGraph state through the checkpointer, without a separate authoritative messages collection. The start checkpoint uses MemorySaver in process memory. Step 1 introduces MongoDBSaver for durable checkpoints and checkpoint_writes. Application code verifies conversation ownership before accessing state. Zod validates inputs and structured model output at runtime. Background: https://dev.to/mongodb/no-messages-table-the-data-model-behind-my-own-claude-based-chatbot-54jp.

AN AGENT IS A GRAPH

Not just a prompt. State, decisions, and a tool-result loop.

START→Load context→Agent→Answer / END
↑Tools → result↓

The LLM selects a callable function. Application code executes it.
The server supplies history; the browser sends only the new message.
Streaming makes both answer text and tool activity visible.

Read: An agent is a graph · DEV ↗
The graph follows START → load_context → agent. The agent either returns an answer or requests a tool. The tools node executes the request and loops back with the result. This cyclical structure supports multi-step work. The browser sends new text and a conversation ID rather than an authoritative transcript. The server checks ownership, and LangGraph restores thread state. An event bridge translates token and tool events into visible UI parts. Relevant files: src/lib/agent.ts and src/lib/stream.ts. Background: https://dev.to/mongodb/an-agent-is-a-graph-43h0.

MongoDB supplies the application's data backend: users, conversation headers, graph checkpoints, memory documents, and the memory vector index. Normal document queries retrieve profile facts, while Atlas Vector Search retrieves semantically relevant facts. Automated Embedding removes application-managed embedding calls. DigitalOcean inference and Tavily search remain external services; one data backend does not mean one service for every responsibility.

SHORT-TERM AND LONG-TERM MEMORY

Short-term memory:
this conversation.

Long-term memory:
useful facts across
conversations.

Retrieve the right context

Short-term: retrieve ordered turns
for the correct session ID.

This app restores checkpoint state
using a stable thread_id.

Long-term: retrieve user-owned
facts for future personalization.

Storage lifetime is not memory scope.
A durable transcript is still thread context.

Short-term memory supplies context within a thread. A basic transcript store retrieves turns for a session ID and orders them by timestamp; unique message IDs or the latest timestamp alone do not reconstruct the conversation. Claudius Minor delegates state persistence to MongoDBSaver and uses thread_id to restore it. Long-term memory stores useful user-owned facts for personalization across threads. A durable transcript is still thread-scoped context, not automatically long-term personal memory.

Step 1 replaces the in-process MemorySaver with MongoDBSaver. A stable thread_id identifies the conversation across requests and server restarts. MongoDBSaver owns the checkpoint storage format; the application does not maintain a second authoritative transcript. Conversation ownership must be verified before returning checkpoint-derived messages. Relevant file: src/lib/checkpointer.ts. Restarting the server and reopening the same thread demonstrates durable state.

Step 2 extracts durable facts from new human and assistant text after the extraction watermark. Tool calls and results are excluded so web-search content does not become a personal fact. Structured model output is validated before persistence. Records include owner, source conversation, category, importance, timestamps, and status. The watermark advances only after successful processing. The displayed JSON is illustrative rather than a complete memory record. Extraction can make mistakes, so memory needs correction and deletion paths.
03

RECALL
PERSONAL
CONTEXT

Filter inside the query

$vectorSearch: {
  index: "memories_vector",
  path: "content",
  query: { text: human },
  numCandidates: 100,
  limit: 10,
  filter: {
    userId: { $eq: owner },
    status: { $eq: "active" },
  },
}
Step 3 uses semantic retrieval to find relevant user memories, including when the query uses different words. Atlas Automated Embedding processes indexed content and search text. The vector query pre-filters by userId and active status inside the search operation. The current recall score floor of 0.65 is an application heuristic, not a universal relevance threshold. Embedding and indexing are asynchronous, so newly stored text may not be immediately searchable. Relevant file: src/lib/agent.ts.

TWO PATHS TO PERSONAL CONTEXT

Profile queries:
important facts.

Vector Search:
relevant facts.

Combine both paths

Load top active memories
with an indexed document query.

Search meaning using
the last three human turns.

De-duplicate the combined context.
If recall fails, keep chat working.

The profile path does not wait for embeddings.
Both paths filter by the current owner.

Personal context combines a document query for important active profile facts and vector search for facts related to the latest three human turns. Both filter by owner. The combined context is de-duplicated, and retrieval failures do not stop chat. A profile query can find a newly stored fact before its vector is searchable. The memories-used UI exposes retrieved context. These operations run in a graph node rather than as model-selected tools in this application.

Step 4 manages memory with insert, skip, and supersede actions. New facts are inserted, duplicates can be skipped, and changed facts can replace earlier active records while preserving supersedes and supersededBy lineage. Step 4 uses semantic neighbors, recent-write checks, and a structured LLM relation comparison so related but distinct facts can coexist. The completed checkpoint matches the reference app implementation. Similarity alone does not establish contradiction. The current two-document lineage update is not atomic. Relevant files: src/lib/memory.ts and src/lib/persistence.ts.
