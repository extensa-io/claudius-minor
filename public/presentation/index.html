Claudius Minor adapts the core ideas of Claudius into a focused learning application: chat, one web-search tool, durable conversation state, and personal memory. The larger Claudius project uses Claude through AWS Bedrock and has a broader scope including model switching, file retrieval, and research workflows. The application uses gpt-oss-120b for both chat and memory extraction through DigitalOcean Serverless Inference. CHAT_MODEL and EXTRACTION_MODEL select the same model; their separate names describe responsibilities. Open weights means model weights are available, not that inference is free or that all training data is public. Next.js, React, and TypeScript provide the application; LangGraph coordinates the agent; Tavily provides web search. MongoDB Atlas stores application data and checkpoints. Atlas Automated Embedding uses Voyage voyage-4 for semantic retrieval, separately from the generative model.

THREE PARTS OF AN AI AGENT

01

Reasoning

The LLM interprets a goal,
plans the next step, and
chooses a tool when needed.

02

Tools

Callable functions let the
agent retrieve data and
act on external systems.

03

Memory

Conversation context and
durable facts help the agent
respond with continuity.

An agent combines reasoning, tools, and memory. A large language model (LLM) interprets the goal and proposes the next action. Application code executes tool functions and handles database access. Memory supplies relevant context to the model; storing a fact does not retrain the model or change its weights.

FIXED WORKFLOW OR AI AGENT?

Airline support example

Known steps?
Use a fixed workflow.

Check for a booking number:
a predictable validation rule.

Non-deterministic Workflow?
Consider an agent.

Resolve a refund request:
inspect the account, evaluate
policy, then take approved actions.

Consequential actions need permissions,
validation, and approval boundaries.

Fixed workflows suit predictable operations such as required-field validation and fixed-category routing. An agent can help when the next action depends on intermediate results, such as coordinating account lookup and refund-policy evaluation. Consequential actions still need permissions, trusted validation, and appropriate approvals. Claudius Minor exposes web search, not financial actions.

Plan an agent by identifying its tasks, required data, and tools. A tool is a callable function for interacting with external systems. Examples include an API for movie information, a database query for profile settings, or vector retrieval for recommendations. In Claudius Minor, only web_search is model-callable. Memory retrieval runs automatically in the load_context graph node.

Read: No messages table · DEV ↗
Access patterns shape the data model. The thread list reads lightweight records from conversations: owner, title, timestamps, and extraction watermark. The current thread reads messages from LangGraph state through the checkpointer, without a separate authoritative messages collection. The start checkpoint uses MemorySaver in process memory. Step 2 introduces MongoDBSaver for durable checkpoints and checkpoint_writes. Application code verifies conversation ownership before accessing state. Zod validates inputs and structured model output at runtime. Background: https://dev.to/mongodb/no-messages-table-the-data-model-behind-my-own-claude-based-chatbot-54jp.

AN AGENT IS A GRAPH

Not just a prompt. State, decisions, and a tool-result loop.

START→Load context→Agent→Answer / END
↑Tools → result↓

The LLM selects a callable function. Application code executes it.
The server supplies history; the browser sends only the new message.
Streaming makes both answer text and tool activity visible.

Read: An agent is a graph · DEV ↗
The graph follows START → load_context → agent. The agent either returns an answer or requests a tool. The tools node executes the request and loops back with the result. This cyclical structure supports multi-step work. The browser sends new text and a conversation ID rather than an authoritative transcript. The server checks ownership, and LangGraph restores thread state. An event bridge translates token and tool events into visible UI parts. Relevant files: src/lib/agent.ts and src/lib/stream.ts. Background: https://dev.to/mongodb/an-agent-is-a-graph-43h0.

LIVE DEMO · THE STARTING APP

LET’S MEET
CLAUDIUS MINOR

Ask from learned knowledge alone.
No tools. No live information yet.

Open the app ↗
The starting application supports streamed chat but has no tools or web-search capability. It answers from learned, parametric knowledge and supplied conversation context, not live evidence. Current-event answers can be stale, incorrect, or appropriately uncertain; an incorrect answer is not guaranteed. Its sidebar lists conversation headers, while the open thread displays graph-state messages. Step 1 adds web search and the tool-result loop. The earlier graph diagram shows the target architecture, not the starting graph. At the start checkpoint, graph state resides in MemorySaver, so restarting the server loses it; long-term memory loading and persistence are not implemented yet. The completed deployed application includes the later steps.
01

GIVE THE
AGENT
TOOLS

Retrieve current evidence

model.bindTools([webSearchTool]);

builder
  .addNode("tools", new ToolNode(tools))
  .addConditionalEdges("agent",
    toolsCondition, ["tools", END])
  .addEdge("tools", "agent");

The model requests a search.
Code executes it. Results return to the model.
Check the answer against its sources.

Step 1 introduces the web_search tool backed by Tavily. A tool schema tells the model which function it can request; application code executes the function. toolsCondition routes tool calls to ToolNode, then results return to the agent for an answer. The app bounds repeated searches to four tool results per turn. Tools supply external evidence without changing the model weights. Search can still fail or return weak sources, and a sourced answer can still be wrong. Before this step the graph has no tool binding or execution node, and it routes directly from agent to END. Relevant files: src/lib/agent.ts, src/lib/search.ts, and src/lib/prompt.ts.

INTEGRATE

LangChain + LangGraph

MongoDBSaver persists graph state.
Use the MongoDB checkpoint
integration.

AUTO-EMBED

Atlas Automated Embedding

Query memories with natural language.
No need to sync, or separate SDKs, Atlas handles the embedding work.

VOYAGE AI

voyage-4 + Vector Search

State-of-the-art embedding models and rerankers.
Text search, vector, hybrid and graph traversal within a unified query interface

MongoDB supplies the application's data backend: users, conversation headers, graph checkpoints, memory documents, and the memory vector index. Normal document queries retrieve profile facts, while Atlas Vector Search retrieves semantically relevant facts. Atlas Automated Embedding uses Voyage AI voyage-4 to embed indexed memory text and text queries. The app supplies an autoEmbed index definition and sends query text, without an embedding SDK or application-managed vector generation. MongoDBSaver comes from @langchain/langgraph-checkpoint-mongodb and persists graph state. Long-term memory documents and vector queries in this app use the MongoDB Node.js driver directly, not a LangChain vector-store wrapper. DigitalOcean inference and Tavily search remain external services; one data backend does not mean one service for every responsibility.

SHORT-TERM AND LONG-TERM MEMORY

Short-term memory

This conversation.

Restore thread context

Retrieve ordered turns for the correct session.
This app restores checkpoint state
using a stable thread_id.

Long-term memory

Useful facts across
conversations.

Recall personal context

Retrieve user-owned facts
for future personalization.
Combine profile queries and vector search.

Short-term memory supplies context within a thread. A basic transcript store retrieves turns for a session ID and orders them by timestamp; unique message IDs or the latest timestamp alone do not reconstruct the conversation. Claudius Minor delegates state persistence to MongoDBSaver and uses thread_id to restore it. Long-term memory stores useful user-owned facts for personalization across threads. A durable transcript is still thread-scoped context, not automatically long-term personal memory.

@langchain/langgraph-checkpoint-mongodb

Step 2 replaces the in-process MemorySaver with MongoDBSaver from @langchain/langgraph-checkpoint-mongodb, the LangGraph MongoDB checkpoint integration in the LangChain ecosystem. A stable thread_id identifies the conversation across requests and server restarts. MongoDBSaver owns the checkpoint storage format; the application does not maintain a second authoritative transcript. Conversation ownership must be verified before returning checkpoint-derived messages. Relevant file: src/lib/checkpointer.ts. Restarting the server and reopening the same thread demonstrates durable state.

Step 3 extracts durable facts from new human and assistant text after the extraction watermark. Tool calls and results are excluded so web-search content does not become a personal fact. Structured model output is validated before persistence. Records include owner, source conversation, category, importance, timestamps, and status. The watermark advances only after successful processing. The displayed JSON is illustrative rather than a complete memory record. Extraction can make mistakes, so memory needs correction and deletion paths.
04

RECALL
PERSONAL
CONTEXT

Agent memory is a RAG app

$vectorSearch: {
  index: "memories_vector",
  path: "content",
  query: { text: human },
  numCandidates: 100,
  limit: 10,
  filter: {
    userId: { $eq: owner },
    status: { $eq: "active" },
  },
}
Step 4 uses semantic retrieval to find relevant user memories, including when the query uses different words. Atlas Automated Embedding uses Voyage AI voyage-4 to process indexed memory content and search text. The query supplies text directly: Atlas handles vector generation, so this app needs no embedding SDK. The autoEmbed field in the index selects voyage-4, while the query selects the index and applies owner filters. The vector query pre-filters by userId and active status inside the search operation. The current recall score floor of 0.65 is an application heuristic, not a universal relevance threshold. Embedding and indexing are asynchronous, so newly stored text may not be immediately searchable. Relevant file: src/lib/agent.ts.

TWO PATHS TO PERSONAL CONTEXT

Profile queries

Important facts.

Load the user’s profile

Retrieve top active memories
with an indexed document query.
No wait for embeddings.

Vector Search

Relevant facts.

Retrieve by meaning

Search using the last three human turns.
Filter by the current owner and active status.
Combine and de-duplicate both paths.

Both paths filter by owner. If recall fails, chat continues without memory.

Personal context combines a document query for important active profile facts and vector search for facts related to the latest three human turns. Both filter by owner. The combined context is de-duplicated, and retrieval failures do not stop chat. A profile query can find a newly stored fact before its vector is searchable. The memories-used UI exposes retrieved context. These operations run in a graph node rather than as model-selected tools in this application.
05

MANAGE
CHANGING
FACTS

Insert · skip · supersede

New fact → insert.
Duplicate fact → skip.
Changed fact → supersede.

Old: I live in Toronto
  status: superseded
  supersededBy → new record

New: I live in Montréal
  status: active
  supersedes → old record
Step 5 manages memory with insert, skip, and supersede actions. New facts are inserted, duplicates can be skipped, and changed facts can replace earlier active records while preserving supersedes and supersededBy lineage. Step 5 uses semantic neighbors, recent-write checks, and a structured LLM relation comparison so related but distinct facts can coexist. The completed checkpoint matches the reference app implementation. Similarity alone does not establish contradiction. The current two-document lineage update is not atomic. Relevant files: src/lib/memory.ts and src/lib/persistence.ts.

Key concepts: reasoning, tools, and memory; task/data/tool planning; fixed versus adaptive workflows; LLM action selection versus application execution; and cyclical graphs.
